Mini Súper

Point-of-sale system for a small grocery store in a rural area.

The store sells, charges and stores everything on its own computer, so it works without internet. From the city, the owner can check the store with a USB drive, a remote connection or a cloud dashboard.

  • Sales and cash register: barcode scanner, keyboard shortcuts, opening and closing the register, configurable VAT.
  • Inventory and purchasing: low-stock alerts and a suggested shopping list based on what sold.
  • Reports: daily profit, best sellers, payroll and worker credit, Excel export.
  • Built for the store: automatic daily backup, USB copy and an installer that makes the system start on its own on Windows.
  • Automated tests for the API, the database, money calculations and syncing.
Security5 measures
  • Passwords hashed with bcrypt. If the user doesn't exist, a dummy hash is compared so the response takes the same time and doesn't reveal which users exist.
  • Session in an httpOnly, SameSite=strict cookie that expires after 12 hours.
  • The server checks the role (admin or cashier) on every request; hiding a button is not the only protection.
  • Content-Security-Policy, X-Frame-Options and nosniff headers, and an API that only accepts JSON.
  • Queries through Sequelize (no hand-built SQL) and every sale in a transaction with row locks, so the till and inventory never end up half-saved.
  • Node.js
  • Express
  • Sequelize
  • PostgreSQL
  • ExcelJS
  • PowerShell

Doo Barber

Appointment system for barbershops, designed to be sold to several businesses.

Clients choose a service, barber, date and time, and book in under a minute without calling. The owner gets a dashboard with the schedule, walk-ins, blocked hours and reports. Each barbershop can set its own color and logo.

  • No double-booking: weekly hours, service duration and blocked hours; the server works out which times are free.
  • Security: hashed password, token sessions, prices that always come from the server and XSS protection.
  • WhatsApp notifications with prefilled messages.
  • I worked section by section, each on its own branch and pull request.
Security5 measures
  • Owner's password hashed with scrypt and a random salt, compared in constant time (timingSafeEqual).
  • After 5 failed attempts from the same IP, login is locked for 15 minutes.
  • Random 32-byte session token; only its SHA-256 hash is stored, and it expires after 7 days.
  • Each service price comes from the database, never from the browser, and the server rejects overlapping bookings.
  • escapeHtml on everything rendered, X-Frame-Options and nosniff headers, and a random cancellation code that cannot be guessed.

Duelo Ronin 1 vs 1

Real-time two-player fighting game in the browser.

Two people join from their browsers and fight two rounds with punches, kicks, jumps and blocks. The server simulates physics and hits; browsers only send key presses.

  • Authoritative server: it computes physics, hits and health; browsers only send keys, so nobody can cheat.
  • Capped at 2: a third visitor sees “Duel full”; if someone disconnects they have 10 seconds to return.
  • Rounds, countdown, rematch and a practice mode against a punching bag while the opponent arrives.
  • 32 automated tests for the game logic and networking.
Security4 measures
  • Authoritative server: physics, hits and health are computed on the server. The browser only reports which keys are pressed, so it cannot send “I won” or teleport the character.
  • Every player message is sanitized: only known buttons with a true/false value are accepted; anything else is dropped.
  • The 2-player limit is enforced on connect: a third visitor gets “Duel full” and never joins the room or receives the fight state.
  • The player ID is validated with a regular expression; if it is invalid, the server issues a new one with crypto.randomUUID.

TecnoAula

School platform with a different dashboard for each role.

Admins, directors, teachers and students each get their own dashboard. Courses are organized in blocks and topics; students see their progress, submit assignments, check their calendar and grades, and take part in forums and chat.

  • Secure sign-in: “Remember me”, failed-attempt limits and token-based password reset.
  • Roles and permissions: a main role plus extra roles and permissions per user.
  • Full courses: blocks, topics, materials, assignments, forums and per-course chat, with each student’s progress.
  • Progress and grade reports per course.
  • Database credentials are kept out of the repository.
Security6 measures
  • Passwords with password_hash, and the session is regenerated on login (session_regenerate_id) to prevent session fixation.
  • Attempt limits: 5 per email and 20 per IP every 15 minutes.
  • CSRF token on every form, compared with hash_equals.
  • “Remember me” with a selector and validator generated with random_bytes, in an httpOnly, SameSite cookie; revoked when the user is disabled.
  • PDO prepared statements, and a 403 response if the role does not match the page.
  • Password reset gives the same response whether or not the email exists, the link lasts 1 hour, and config.php with the credentials stays out of the repository.

Security in my projects

I study cybersecurity, so I apply it to what I build. These are the practices I use; each link opens the screen where you can see it at work.

Passwords nobody can read

No password is stored in plain text: a salted hash (bcrypt or scrypt) is stored and compared in constant time.

Where I applied it

  • Doo Barber: scrypt with random salt
  • Mini Súper: bcrypt
  • TecnoAula: password_hash
  • Grades portal

Brute-force protection

After several failed attempts, login is locked for a while, per user and per IP address.

Where I applied it

  • Doo Barber: 5 attempts per IP, 15-min lockout
  • TecnoAula: 5 per email and 20 per IP in 15 min

Secure sessions

The session is regenerated on login to prevent session fixation, cookies are httpOnly and SameSite, and tokens are stored hashed and expire.

Where I applied it

  • Doo Barber: 32-byte token hashed with SHA-256, 7 days
  • Mini Súper: httpOnly, SameSite=strict 12-hour cookie
  • TecnoAula: “Remember me” with selector and validator; revoked when the user is disabled

No SQL injection

User input is never concatenated into a query: prepared statements or the ORM are used.

Where I applied it

  • TecnoAula: PDO prepared statements
  • Grades portal: prepared mysqli
  • Mini Súper: Sequelize

XSS and CSRF protection

All user text is escaped before rendering, and forms that change data carry a token or only accept same-site JSON.

Where I applied it

  • TecnoAula: CSRF token on every form
  • Doo Barber: escapeHtml on everything rendered
  • Mini Súper: Content-Security-Policy and JSON-only API

The server decides, not the browser

Permissions, prices and rules are validated on the server. Hiding a button isn't enough: if someone sends the request by hand, the server rejects it.

Where I applied it

  • Mini Súper: role checked on every request
  • TecnoAula: 403 if the role does not match
  • Doo Barber: price comes from the database, not the browser
  • Catalog: ignores tampered products and prices
  • Duelo Ronin: authoritative server against cheating

Don't leak information

Responses don't reveal whether a user exists, and public identifiers can't be guessed.

Where I applied it

  • Mini Súper: dummy hash so timing is equal
  • TecnoAula: same reset response either way; 1-hour link
  • Doo Barber: random cancellation code

Consistent data, secrets out of the code

Money and inventory operations are transactions that never save halfway, and credentials live outside the repository.

Where I applied it

  • Mini Súper: transaction with row locks
  • Doo Barber: booking queue with no double-booking
  • TecnoAula: config.php kept out of the repo
